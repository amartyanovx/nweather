# Правила основной сессии

Читай перед работой. Общие ограничения для всех агентов — `AGENTS.md`; здесь процесс, проверки, приёмка, завершение
основной сессии и Memory Bank. Reviewer этот файл не читает и не применяет.

## Разведка и план

- Объём разведки — под задачу: для багфикса карта архитектуры избыточна
- Очевидная правка в одном-двух файлах, вопрос, разведка — без плана и ревью
- План и его независимое ревью обязательны для Engineering-планов: меняются публичный контракт, формат или схема данных,
  архитектурные границы, безопасность, зависимости, сборка; операция необратима; причина дефекта и решение неочевидны.
  Признак: последствия правки нельзя оценить по diff
- План: цель и критерии приёмки · модули и файлы · шаги · риски и способы их снять · тест-план. Готовое решение
  пользователя — вход для плана, а не замена плану и ревью
- Реализация — после согласованного плана; отклонился — обнови план. Замечания принимай или отклоняй с аргументом; после
  существенных правок — новый круг; разногласия после второго круга решает человек
- Ревью реализации — когда риск велик (контракт, данные, безопасность, крупный рефакторинг, необратимые операции);
  вердикт сверяй с кодом и прогонами, а не с отчётом

## Независимое ревью

- Reviewer — сессия с изолированным контекстом: без истории основной сессии и без записи в проект; вердикт и замечания
  сверяются с кодом и прогонами, а не с отчётом агента
- Роль, границы и шкала — `harness/reviewer.md`; механика запуска — ниже, §«Как запустить reviewer»
- Итоговый ответ ревью читай целиком: вердикт и замечания — из полного текста, а не из последних строк; сохрани их в
  контекст задачи
- Независимое ревью недоступно или прогон не работает — ревью нет: саморевью за него не выдавай и сообщи конкретное
  препятствие

### Как запустить reviewer

- Reviewer запускает основная сессия как отдельный экземпляр агента или отдельную сессию субагента — средствами
  фактического окружения. Способ запуска правилами не фиксируется; обязательны свойства ниже
- Изоляция контекста обязательна: у reviewer нет истории основной сессии, вход — задание, тот же проект и read-only
  команды
- Запрет записи в проект безусловен. Если окружение умеет технически отключить инструменты записи — отключи их; если нет,
  запрет держится на правилах и проверяется snapshot-контролем
- Задание передаётся reviewer целиком в начале сессии: «прочитай `harness/reviewer.md` и работай по нему;
  `harness/main-session.md` не читай»; сценарий (план или реализация); требования; ограничения проекта; план либо
  снимок области изменений с базой; прогоны — команда, статус, где лог; запреты — правки файлов проекта, установка
  пакетов, миграции, seed, сборка, commit
- Если окружение принимает задание файлом или пишет лог сессии, файлы — в системном temp вне репозитория. Пути к логам
  прогонов передавай reviewer как свидетельство результатов проверок
- Snapshot-контроль обязателен и проверяет конечное состояние: до запуска и после завершения сессии reviewer выполни
  `npm run reviewer:snapshot` и сравни вывод. Снимок покрывает HEAD, tracked/untracked файлы, staged/unstaged изменения и
  содержимое untracked-файлов. Ignored-данные снимок не контролирует: ignored-пути целиком не входят (см. `.gitignore`),
  поэтому установка зависимостей, тесты, сборка, seed и миграции им не обнаруживаются — их запрет остаётся правилом
  reviewer. Снимок не предотвращает запись и не обнаруживает изменение, отменённое до финального снимка. Вывод не совпал
  или команда упала — вердикт reviewer не принимай, зафиксируй нарушение и не выдавай ревью за состоявшееся
- Для PR база — `git merge-base <целевая ветка> HEAD`; укажи способ получить diff и состав изменений (закоммиченные,
  staged, unstaged, новые файлы). Область неоднозначна — напиши это, а не подставляй предположение

## Проверки

| Проверка              | Когда запускать                                                            |
| :-------------------- | :------------------------------------------------------------------------- |
| линт и проверка типов | после каждой правки кода                                                   |
| форматирование        | после правок любых файлов — точечно, по изменённым файлам                  |
| unit-тесты            | изменена логика или тесты                                                  |
| E2E                   | изменено наблюдаемое поведение или публичный контракт                      |
| мутации               | новые или существенно изменённые unit-тесты — только по изменённым модулям |
| сборка                | затронуты сборка, зависимости, нативная часть; перед сдачей задач с кодом  |

- Линт, проверка типов и форматирование изменённых файлов обязательны; остальные проверки — по матрице выше
- Команды, пороги и охват — `memory-bank/techContext.md`; стек проектный, новый не внедряй
- Проверка валидна только для того содержимого, на котором получена: после правок затронутые проверки повторяются; без
  повода не запускай; дорогие шаги (E2E, мутации, сборка) — с обоснованием в отчёте
- `npm run quality-gate` запускается автоматически pre-push-хуком при каждом push из worktree: полный набор стадий,
  FAIL блокирует push. Хук — `.githooks/pre-push` → `scripts/pre-push.mts`; установка — `prepare` после
  `npm ci`/`npm install` (`scripts/install-hooks.mts`: `core.hooksPath`, executable-бит; режим `100755` зафиксирован в
  индексе, `core.fileMode` установщик не меняет), для существующего worktree — `npm run hooks:install`.
  `git config --get core.hooksPath` (ожидается `.githooks`) показывает конфигурацию, а не работоспособность хука:
  фактическая проверка — push или прямой запуск `.githooks/pre-push` (POSIX: `sh .githooks/pre-push </dev/null` —
  полный прогон gate). При замене другого `core.hooksPath` установщик печатает прежнее значение и источник: локальное
  значение возвращается `git config core.hooksPath "<прежнее>"`, глобальное — снятием локального переопределения
  `git config --unset core.hooksPath`. `core.hooksPath` общий для worktrees, поэтому worktree без `.githooks` молча не
  запускает хук
- Push только удалений веток и тегов gate пропускает; без `node_modules` push блокируется сообщением о `npm ci`. Хук
  проверяет текущее worktree/HEAD, а не запушенный ref: push другого ref из грязного или отставшего worktree полностью
  не валидируется — барьер остаётся за CI
- Аварийный обход — `git push --no-verify`; причина и непройденная проверка фиксируются в отчёте. Без прямого указания
  пользователя обход не применяется
- Локальный ACK правок Harness/CI хук подставляет сам — SHA текущего HEAD. Это сигнал для guard, а не авторизация:
  авторизация и установка `HARNESS_ACK_SHA` — `AGENTS.md` §«Полномочия»; required status checks GitHub
  («AI Quality Gate (static)», «Build») остаются условием merge, агент их не ожидает. `Tests` и `Build` в
  условия сдачи агента не входят; локальная сборка — по матрице проверок. Подмножество стадий для диагностики —
  `npm run quality-gate -- <стадия>`
- Локальный прогон невозможен (нет зависимостей) — сообщи это как ограничение; не выдавай CI за локальный
- Изменённые файлы форматируй точечно, а не `npm run format` (команды и их область — `memory-bank/techContext.md`).
  Критерий приёмки — `prettier --check` по изменённым файлам
- Списки оформляй через `-` с отступами для вложенности: символ `•` Prettier схлопывает в абзац

## Приёмка и отчёт

- С открытыми Blocking/Major задача не сдаётся; Minor исправляются или фиксируются в отчёте. Шкала и условие `approve` —
  `harness/reviewer.md` §«Шкала замечаний»
- Саморевью — при изменениях с нетривиальными последствиями, которые нельзя оценить непосредственно по diff; независимое
  ревью им не подменяется
- Отчёт оформляй строго по форме, в этом порядке:
  1. Что реализовано
  2. Проверки и фактический результат
  3. Статус ревью и вердикт
  4. Оставшиеся ограничения и нерешённое

  Пути — относительно корня проекта. Разделы не переименовывай и не заменяй своей структурой.

- PR — полноценное описание, а не заголовок: что и зачем сделано, изменения по областям и файлам, проверки и их
  результаты, риски, ограничения и оставшиеся шаги
- Коммит, push и merge сам не выполняешь и не напоминаешь — только по прямому запросу

## Завершение задачи

- Гаси процессы этой задачи, сессию reviewer и зависшие команды своих прогонов (dev-сервер, `npm start`, E2E) средствами
  фактического окружения; порты проекта не оставляй занятыми. Фоновые задачи запускай только с известным идентификатором
  процесса и дожидайся их завершения
- Временные файлы, логи, задание и лог reviewer удаляй сразу после использования; процессы, конфиги, данные и порты,
  которых не создавал в этой задаче, не трогай

## Ограничения

- **Итерации:** ≤10 существенных циклов на задачу (меняются файлы или план); не повторяй неудачный способ исправления без
  новых данных о причине дефекта; на пределе — фиксация нерешённого и решение человека

## Memory Bank

- Состояние проекта в документах не хранится (источник — код и `git log`); архитектуру и технические решения фиксируй при
  их изменении
- Memory Bank — часть завершения задачи, а не follow-up: при изменении архитектуры или технических решений обнови
  `techContext.md` / `systemPatterns.md`, чекпоинт `local/activeContext.md` — после каждой задачи (правила —
  `memory-bank/maintenance.md`, `memory-bank/activeContextRules.md`). Пропуск — задача не сдана
- В этом файле — только ссылки на правила банка и бюджет загрузки задачи; правила ведения — в `maintenance.md` и
  `activeContextRules.md`, маршрутизация — в `index.md`
