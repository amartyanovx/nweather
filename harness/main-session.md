# Правила основной сессии

Читай перед работой. Общие ограничения — `AGENTS.md`; здесь процесс, проверки, приёмка, завершение и Memory Bank.
Reviewer этот файл не читает и не применяет.

## Разведка и план

- Объём разведки — под задачу: для багфикса карта архитектуры избыточна. Очевидная правка в одном-двух файлах, вопрос и
  разведка — без плана и ревью
- План и его независимое ревью обязательны, если меняются публичный контракт, формат или схема данных, архитектурные
  границы, безопасность, зависимости или сборка; операция необратима; причина дефекта и решение неочевидны. Признак:
  последствия правки нельзя оценить по diff
- План: цель и критерии приёмки · модули и файлы · шаги · риски и способы их снять · тест-план. Готовое решение
  пользователя — вход для плана, а не замена плану и ревью
- Реализация — после согласованного плана; отклонился — обнови план. Замечания принимай или отклоняй с аргументом; после
  существенных правок — новый круг; разногласия после второго круга решает человек
- Ревью реализации обязательно при высоком риске, крупном рефакторинге, изменениях контракта, данных или безопасности,
  неочевидных исправлениях, а также рисках, выявленных в ходе реализации. Число изменённых файлов само по себе не
  освобождает. Вердикт сверяй с кодом и прогонами, а не с отчётом

## Независимое ревью

- Reviewer — отдельная сессия с изолированным контекстом: без истории основной сессии и без записи в проект. Роль,
  границы и шкала — `harness/reviewer.md`
- Итоговый ответ читай целиком: вердикт и замечания — из полного текста, сохрани их в контекст задачи
- Независимое ревью недоступно или прогон не работает — ревью нет: саморевью за него не выдавай, сообщи конкретное
  препятствие
- Задание передаётся целиком в начале: «прочитай `harness/reviewer.md` и работай по нему; `harness/main-session.md` не
  читай»; сценарий (план или реализация), требования, ограничения проекта, план либо снимок области изменений с базой,
  прогоны (команда, статус, где лог), запреты: правки, установка пакетов, миграции, seed, сборка, commit
- Запрет записи безусловен. Если окружение умеет технически отключить инструменты записи — отключи; иначе запрет держится
  на правилах и проверяется snapshot-контролем. Файлы задания и логов — в системном temp вне репозитория
- Snapshot-контроль: до и после сессии reviewer выполни `npm run reviewer:snapshot` и сравни вывод. Покрытие — HEAD,
  tracked/untracked, staged/unstaged, содержимое untracked. Ignored-пути не входят, поэтому установка, тесты, сборка, seed
  и миграции им не обнаруживаются; снимок не предотвращает запись и не видит изменение, отменённое до финального снимка.
  Вывод не совпал или команда упала — вердикт не принимай, зафиксируй нарушение
- Для PR база — `git merge-base <целевая ветка> HEAD`; укажи способ получить diff и состав изменений (закоммиченные,
  staged, unstaged, новые файлы). Область неоднозначна — напиши это, а не подставляй предположение

## Проверки

| Проверка              | Когда запускать                                                            |
| :-------------------- | :------------------------------------------------------------------------- |
| линт и проверка типов | после логически связанной серии правок и перед сдачей                      |
| форматирование        | после правок любых файлов — точечно, по изменённым файлам                  |
| unit-тесты            | изменена логика или тесты                                                  |
| E2E                   | изменено наблюдаемое поведение или публичный контракт                      |
| мутации               | новые или существенно изменённые unit-тесты — только по изменённым модулям |
| сборка                | затронуты сборка, зависимости, нативная часть; перед сдачей задач с кодом  |

- Линт, проверка типов и форматирование изменённых файлов обязательны; остальные проверки — по матрице. Команды, пороги
  и охват — `memory-bank/techContext.md`; стек проектный, новый не внедряй
- При изменении контрактов проверки — после обновления затронутых потребителей, а не после каждой промежуточной правки.
  После новых изменений повторяй затронутые проверки; без повода не запускай; дорогие шаги (E2E, мутации, сборка) — с
  обоснованием в отчёте
- `npm run quality-gate` — обязательная проверка перед push: pre-push-хук запускает полный набор стадий, FAIL блокирует
  push. Механика хука, CI и ACK — `memory-bank/techContext.md`; авторизация — `AGENTS.md` §«Полномочия». Локальный ACK —
  сигнал, не авторизация. Required status checks GitHub остаются условием merge, агент их не ожидает; `Tests` и `Build` в
  условия сдачи не входят
- Ошибка проверки — устрани причину и повтори затронутую проверку; не подавляй диагностику и не снижай порог. Локальный
  прогон невозможен (нет зависимостей) — это ограничение, не выдавай CI за локальный
- `git push --no-verify` — только по прямому указанию пользователя; причину и непройденную проверку фиксируй в отчёте
- Изменённые файлы форматируй точечно, а не `npm run format`; критерий — `prettier --check` по изменённым файлам

## Приёмка и отчёт

- С открытыми Blocking/Major задача не сдаётся; Minor исправляются или фиксируются в отчёте. Шкала и условие `approve` —
  `harness/reviewer.md`
- Саморевью — при нетривиальных последствиях, которые нельзя оценить по diff; независимое ревью им не подменяется
- Отчёт строго по форме, в этом порядке: 1. Что реализовано; 2. Проверки и фактический результат; 3. Статус ревью и
  вердикт; 4. Оставшиеся ограничения и нерешённое. Пути — относительно корня проекта; разделы не переименовывай
- PR — полноценное описание: что и зачем, изменения по областям и файлам, проверки и результаты, риски, ограничения,
  оставшиеся шаги

## Завершение задачи

- Гаси процессы этой задачи (dev-сервер, `npm start`, E2E), сессию reviewer и зависшие команды своих прогонов; порты
  проекта не оставляй занятыми. Фоновые задачи — только с известным идентификатором и дожидайся их завершения
- Временные файлы, логи, задание и лог reviewer удаляй после использования. Процессы, конфиги, данные и порты, которых не
  создавал в этой задаче, не трогай

## Ограничения

- **Итерации:** ≤10 существенных циклов на задачу (меняются файлы или план); не повторяй неудачный способ исправления без
  новых данных о причине; на пределе — фиксация нерешённого и решение человека

## Memory Bank

- Состояние проекта в документах не хранится (источник — код и `git log`); архитектуру и технические решения фиксируй при
  их изменении
- Чекпоинт `memory-bank/local/activeContext.md` — после каждой задачи, перед итоговым ответом; архитектурные изменения —
  `techContext.md` / `systemPatterns.md`. Пропуск — задача не сдана. Правила — `memory-bank/maintenance.md`,
  `memory-bank/activeContextRules.md`; маршрутизация — `memory-bank/index.md`
