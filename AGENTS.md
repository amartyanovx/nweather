## 2. Принципы разработки

### Архитектура Next.js

- Server Components по умолчанию: используй Server Components, если только не требуется клиентская интерактивность или
  доступ к браузерным API.
- Минимизация Client Components: изолируй клиентскую логику в компонентах минимально необходимого размера.
- Получение данных: по возможности выполняй запросы на сервере в Server Components. Используй клиентские запросы,
  когда этого требует функциональность.
- Потоковая загрузка: используй границы Suspense там, где они улучшают загрузку интерфейса и пользовательский опыт.
- Следуй соглашениям Next.js App Router и используй встроенные возможности фреймворка.
- Поведение Next.js-специфичных API сверяй по документации в `node_modules/next/dist/docs/`: открывай конкретные файлы
  по пути, поиск по `node_modules` ограничен `.clineignore`.

### TypeScript

- Используй строгую типизацию. Не используй `any`; если тип неизвестен предпочитай `unknown`.
- Явно указывай типы пропсов компонентов и публичных интерфейсов функций.
- Используй `interface` или `type` в зависимости от структуры данных и существующих соглашений проекта.
- Для сущностей Next.js используй встроенные типы, например `PageProps`, `LayoutProps` и `Metadata`, когда они применимы.
- Избегай необоснованных утверждений типов и небезопасных преобразований.

### Качество кода

- Отдавай предпочтение простым, понятным и сопровождаемым решениям.
- Избегай избыточных абстракций, зависимостей и преждевременной оптимизации.
- Следуй существующим соглашениям проекта, прежде чем вводить новые подходы.
- Каждый компонент и модуль должен иметь чёткую зону ответственности.
- Выноси код в отдельные модули, если это улучшает читаемость, повторное использование или сопровождаемость.
- Один файл — один экспортируемый компонент. Лимит 200 строк действует для модулей `src/**`; тесты и конфиги не
  ограничены.
- Предпочитай декларативный и иммутабельный подходы, когда они делают код понятнее.
- Соблюдай единые правила именования:
  - компоненты и типы — PascalCase (`Header`, `WeatherDay`);
  - функции, переменные и хуки — camelCase (`useWeather`, `useCityWeeklyWeather`);
  - файлы компонентов — PascalCase по имени компонента (`Header.tsx`, `BaseContainer.tsx`);
  - хуки — файл camelCase с префиксом `use` (`useWeather.ts`);
  - служебные модули и роуты — kebab-case или по соглашению App Router (`fetcher.ts`, `route.ts`).
- Не добавляй комментарии, которые просто повторяют смысл кода.
- Добавляй комментарии, если они объясняют неочевидные решения, ограничения или сложную логику.
- Форматируй только изменённые файлы: `npx prettier --write <файлы>`. Глобальный `npm run format` переписывает
  инструкции (`.clinerules/**`, `AGENTS.md`) и конфиги — не используй его.

## 3. Команды проекта

| Команда                | Назначение                       | Ограничения и предусловия                                                                                          |
| ---------------------- | -------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| `npm run dev`          | dev-сервер Next.js               | занимает порт 3000; не оставляй процесс запущенным после задачи                                                    |
| `npm run lint`         | oxlint                           | быстрый, запускай после изменений                                                                                  |
| `npm run typecheck`    | проверка типов (`tsc --noEmit`)  | запускай после изменений кода                                                                                      |
| `npm test`             | Jest с покрытием                 | `coverageThreshold` 85% по statements/branches/functions/lines; пишет каталог `coverage/`                          |
| `npm run e2e`          | Playwright                       | нужен существующий `dev.db`; `webServer` выполняет `npm run build && npm start` на порту 3000 (timeout 120 с)       |
| `npm run mutate`       | Stryker                          | длительный прогон, правила в разделе 4                                                                             |
| `npm run build`        | production-сборка                | пишет `.next/`, использует нативный `better-sqlite3`                                                               |
| `npm run format`       | глобальное форматирование        | не использовать: переписывает инструкции и конфиги, см. раздел 6                                                   |
| `npm run format:check` | проверка форматирования Prettier | baseline не зелёный, см. раздел 6                                                                                  |

## 4. Тестирование

Модульные тесты (Jest)

- Размещай unit-тесты в `__tests__/` (включая `__tests__/api/`), имя файла — `<модуль>.test.ts(x)`.
- Следуй существующим соглашениям по мокам: CSS-модули мокаются в `jest.setup.ts`, модули проекта — по алиасу `@/*`
  через `jest.mock`.
- Покрывай основные сценарии, граничные случаи и обработку ошибок.
- Уделяй особое внимание ошибкам API, некорректному JSON и пустым ответам, когда это применимо.
- Следи за порогом покрытия: `npm test` падает при снижении ниже 85%.

E2E-тесты (Playwright)

- Размещай E2E-тесты в `tests/` с суффиксом `.spec.ts`.
- Не смешивай наборы: файл `.test.ts(x)` в `tests/` тоже подхватывается Jest — так сейчас работает
  `tests/WeatherTabs.test.tsx`.
- Полагайся на наблюдаемое поведение приложения, а не на внутренние детали реализации.
- Критичные сценарии: загрузка данных, переключение вкладок, обработка ошибок.

Мутационное тестирование (Stryker)

- Конфигурация `.stryker.config.js`: мутируется `src/**/*.{ts,tsx}` без `src/lib/{db,schema,seed}.ts`,
  `coverageAnalysis: 'perTest'`, `disableTypeChecks`, thresholds 90/80, break 75.
- Обязательно после добавления или существенного изменения unit-тестов: прогоняй
  `npx stryker run --mutate src/<путь>/<файл>.ts` для затронутого модуля; полный `npm run mutate` — если изменения
  затрагивают несколько модулей.
- Цель — отсутствие выживших мутантов, кроме эквивалентных; эквивалентные фиксируй в отчёте с обоснованием.
- Мутанты не проверяются типами (`disableTypeChecks`), поэтому мутационный прогон не заменяет `npm run typecheck`.
- Прогон длительный: не запускай его без необходимости и не подавляй вывод.

Проверка качества

- После изменений запускай `npm run lint`, `npm run typecheck` и `npm test`; E2E — если затронуто поведение приложения.
- Исправляй регрессии, вызванные внесёнными изменениями.
- Не утверждай, что тесты или проверки прошли успешно, если они фактически не выполнялись.

## 5. Данные и база

- `dev.db` — локальный файл SQLite, не под контролем версий: его удаление необратимо.
- Не запускай `node seed.js` и `src/lib/seed.ts`, не удаляй и не пересоздавай `dev.db`, не выполняй миграции без явного
  разрешения.
- Схема — `src/lib/schema.ts`, подключение — `src/lib/db.ts`, конфигурация drizzle-kit — `drizzle.config.ts`.
- API route `/api/weather` читает данные через Drizzle ORM; для E2E требуется уже наполненная база.

## 6. Форматирование

- Конфигурация — `.prettierrc.json`, игнорируемые файлы — `.prettierignore`.
- Списки оформляй через `-` с отступами для вложенности: символ `•` Prettier схлопывает в абзац и структура теряется.
- Проверяй форматирование только изменённых файлов: `npx prettier --check <файлы>`.
- `npm run format:check` сейчас не зелёный (baseline — 25 файлов, включая конфиги и часть тестов), поэтому он не
  используется как критерий приёмки до отдельной задачи по нормализации форматирования.
- Глобальный `npm run format` не запускай: он переписывает инструкции (`.clinerules/**`, `AGENTS.md`) и конфиги.
