# Project Overview

## 1. Контекст проекта
nweather — приложение погоды на базе Next.js 16 App Router и TypeScript.

Знания о проекте хранятся в memory-bank/.

Правила загрузки контекста
• Перед началом работы изучи memory-bank/index.md, чтобы определить, какая документация относится к текущей задаче.
• Загружай только те документы Memory Bank, которые необходимы для выполнения задачи.
• Не читай весь Memory Bank без конкретной необходимости.
• При необходимости обращайся к дополнительной документации по мере работы.
• Считай задокументированные архитектурные решения и соглашения проекта основным источником информации.
• Если документация отсутствует или противоречит фактической реализации, сначала выясни причину, а не делай предположений.

## 2. Принципы разработки
Архитектура Next.js
• Server Components по умолчанию: Используй Server Components, если только не требуется клиентская интерактивность или доступ к браузерным API.
• Минимизация Client Components: Изолируй клиентскую логику в компонентах минимально необходимого размера.
• Получение данных: По возможности выполняй запросы на сервере в Server Components. Используй клиентские запросы, когда этого требует функциональность.
• Потоковая загрузка: Используй границы Suspense там, где они улучшают загрузку интерфейса и пользовательский опыт.
• Следуй соглашениям Next.js App Router и используй встроенные возможности фреймворка.

TypeScript
• Используй строгую типизацию. Не используй any; если тип неизвестен, предпочитай unknown.
• Явно указывай типы пропсов компонентов и публичных интерфейсов функций.
• Используй interface или type в зависимости от структуры данных и существующих соглашений проекта.
• Для сущностей Next.js используй встроенные типы, например PageProps, LayoutProps и Metadata, когда они применимы.
• Избегай необоснованных утверждений типов и небезопасных преобразований.

Качество кода
• Отдавай предпочтение простым, понятным и сопровождаемым решениям.
• Избегай избыточных абстракций, зависимостей и преждевременной оптимизации.
• Следуй существующим соглашениям проекта, прежде чем вводить новые подходы.
• Каждый компонент и модуль должен иметь чёткую зону ответственности.
• Выноси код в отдельные модули, если это улучшает читаемость, повторное использование или сопровождаемость.
• Предпочитай декларативный и иммутабельный подходы, когда они делают код понятнее.
• Соблюдай единые правила именования:
  • Компоненты и типы: PascalCase.
  • Функции, переменные и хуки: camelCase.
  • Файлы и директории: kebab-case, если соглашения фреймворка не требуют иного.
  • Не добавляй комментарии, которые просто повторяют смысл кода.
  • Добавляй комментарии, если они объясняют неочевидные решения, ограничения или сложную логику.

## 3. Тестирование
Модульные тесты
• Используй Jest с TypeScript.
• Следуй существующей структуре директории __tests__/ и соглашениям по созданию моков.
• Покрывай основные сценарии, граничные случаи и обработку ошибок.
• Уделяй особое внимание ошибкам API, некорректному JSON и пустым ответам, когда это применимо.

E2E-тесты
• Используй Playwright.
• Размещай E2E-тесты в директории tests/.
• Уделяй основное внимание критически важным пользовательским сценариям, включая загрузку данных, переключение вкладок и обработку ошибок.
• Предпочитай проверку наблюдаемого поведения приложения проверке внутренних деталей реализации.

Проверка качества
• Запускай соответствующие тесты после изменения кода.
• По возможности запускай линтер и проверку типов.
• Исправляй регрессии, вызванные внесёнными изменениями.
• Не утверждай, что тесты или проверки прошли успешно, если они фактически не были выполнены.
